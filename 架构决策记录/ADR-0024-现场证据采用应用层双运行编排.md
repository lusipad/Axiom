# ADR-0024：现场证据采用应用层双运行编排

- 状态：Accepted
- 日期：2026-08-13

## 背景

R7-E 已能核验一次 Beckhoff Shadow capture，R4.1 已能消费两个有类型 evidence pair 做 calibration/holdout 验证，但 v0.18.0 的外部 R7-E assessment 会把调用方输入投影到共享默认 Case。现场人员还需要手工从两份 assessment 拼装 pair，容易丢失 Case 身份或绕过门禁顺序。

可以新增 R7-F DomainPack，也可以在应用层编排既有 R7-E 与 R4.1。前者会重复现有 Artifact、Metric 和 Claim；后者只负责保持输入身份和执行顺序，不改变领域真值。

## 决策

新增版本化的 `axiom.field-evidence-assessment-request@1` / `report@1`，作为应用层 dossier 编排器，而不是新 DomainPack：

1. calibration 与 validation 分别携带完整 `R7EAssessmentRequest`，一旦包含 command 或 Shadow evidence 就必须显式提供 `caseId`；
2. 两个 `caseId` 必须精确相等，pair ID 必须不同；
3. 编排器分别重放两个 R7-E assessment，只有两个 deployment Shadow gate 都为 `Passed` 才创建有类型 pair；
4. 两个 pair 交给既有 R4.1 evaluator，独立性、同设备、采样周期、对齐、holdout fit 与残差分解继续由 R4.1 判定；
5. 报告保留两份 R7-E 结果、两个可选 pair、完整 R4.1 结果、分层状态和确定性内容哈希。

`overallStatus=Passed` 只表示 `single-device-case-scoped` reality gate 通过。Controlled Trial 与 Closed Loop 固定为 `Open`，DeviceSafe 与 ProcessSafe 固定为 `NotAssessed`。

## 后果

- Python API、CLI、HTTP 和网页共享同一个确定性编排函数，不再由客户端复制门禁逻辑。
- R7-E、R4.1 的 DomainPack、Metric 和 Claim 保持唯一来源；Core 不需要修改。
- 公开示例仍只有 Open 输入；测试中的合成完整证据不能冒充现场现实证据。
- 若未来需要跨主机持久化、审批和数据保留策略，应增加外部作业系统，不能把路径读取、凭据或隐式存储塞进该请求模型。

## 被拒方案

- 新增 R7-F DomainPack：只会包装两个已存在的 evaluator，并重复 Claim 与运行时绑定。
- 允许客户端直接提交 pair：会跳过 R7-E 重放，无法证明 pair 来自本次核验结果。
- 继续使用共享默认 Case：不同现场任务可能被错误归并，破坏 applicability 与 holdout 语义。
- 把双运行结果压成综合分数：会隐藏 Open、Blocked、Refuted 及安全状态之间的区别。

### Verification

- Open、Passed、Blocked、Refuted、跨 Case 拒绝、内容篡改、CLI/HTTP 确定性和 UI stale-result 回归测试通过。
- 生产路径不连接 PLC，不包含 OPC UA Write/Method Call，也不发布新的安全 Claim。
- 未连接真实 TwinCAT/TF6100；现实通过、受控试验、闭环运行与功能安全仍是外部门禁。
